# 0007 — Область решения света

## Решение

Solve света ограничен окном колонок: видимая область плюс
`WORLD_LIGHT_WINDOW_MARGIN` = 128 световых cells. Оба канала решаются в одном
проходе.

## Контекст

Замер (`make bench`, строка `lighting`) показал 10.19 ms на кадр, как только
фонарь игрока сдвигался больше чем на полсветовой ячейки — то есть в полёте
каждый кадр. При 120 FPS бюджет кадра — 8.3 ms; свет один съедал больше всего
бюджета. Причина: solve шёл по всему полю 2048×108, при том что игрок видит
около 80 колонок.

## Почему запас 128

Открытый воздух пропускает 0.97 на световую ячейку, поэтому источник за
границей окна приходит к видимому краю с коэффициентом 0.97¹²⁸ ≈ 2% — ниже
шага квантования (1/512), с которым сравнивает renderer, и ниже того, что может
показать байт на канал.

Канал неба окно не портит принципиально: он заполняется проходом по столбцу
сверху, а столбец решается независимо от соседей.

## Результат

| Режим | до | после |
|---|---:|---:|
| движущийся фонарь | 10.189 ms | 1.732 ms |
| p95 | 11.612 ms | 2.340 ms |
| бурение каждый кадр | 10.108 ms | 1.649 ms |

## Отвергнуто по замеру: разделение каналов

Идея выглядит правильной: sky меняется только вместе с рельефом, поэтому
движущийся фонарь мог бы solve-ить только ember. Реализовано и измерено —
полёт выиграл 0.2 ms, а бурение подорожало с 1.6 до 3.2 ms, потому что каналы
делят между собой поиск transmission и весь расчёт индексов, а бурение —
основной глагол этой игры. Разделение откачено; причина записана в комментарии
рядом с `WorldSolveLight`, чтобы её не «улучшили» обратно.
